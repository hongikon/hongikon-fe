# 학생 생활 팁 공지 설계 (초안)

학교 공지(크롤링)와 별개로, **운영자가 직접 쓰는 "학생 생활 팁"** 을 한 갈래로 제공한다.
수강신청·장학·시설 이용처럼 공지에는 안 나오지만 학생에게 유용한 정보가 대상이다.

> 이 문서는 설계 초안이다. 코드는 아직 바꾸지 않았다. 아래 "확인 필요"가 정해지면 구현에 들어간다.

## 1. 기존 구조와의 관계

| 구분 | 출처 | 저장 | 성격 |
|---|---|---|---|
| 학교 소식 | 학교·학과 게시판 크롤링 | `news` 테이블 / `crawledNews.ts` | 자동 수집, 출처별 구독 |
| 앱 공지 | 운영자 | `constants/appNotices.ts` (하드코딩) | 앱 자체 안내, 설정 화면 |
| **학생 팁 (신규)** | 운영자 직접 작성 | 1단계 정적 JSON → 2단계 `tips` 테이블 | 큐레이션, 오래 유효 |

팁은 크롤링 소식과 **수명이 다르다**. 소식은 날짜가 지나면 묻히지만 팁은 학기마다 다시 읽힌다.
그래서 `news`에 섞지 않고 별도 모델로 둔다.

## 2. 콘텐츠 모델

```ts
type TipCategory =
  | 'course'      // 수강신청·학사
  | 'scholarship' // 장학·학자금
  | 'facility'    // 시설·도서관·프린트 등 이용법
  | 'food'        // 식당·제휴 혜택
  | 'commute'     // 통학·교통
  | 'admin'       // 휴복학·증명서·행정
  | 'wellbeing'   // 상담·건강

interface Tip {
  id: string
  category: TipCategory
  title: string            // 한 줄 요약
  body: string             // 본문 (짧게, 마크다운 최소 지원)
  buildingId?: string      // 지도 연결: 관련 건물
  partnerId?: string       // 제휴 정보 연결
  linkUrl?: string         // 근거가 되는 학교 공지·페이지
  season?: 'spring' | 'fall' | 'always'   // 학기 시작 등 시기성 노출용
  pinned: boolean          // 상단 고정
  publishedAt: string      // ISO 8601
  updatedAt: string        // 내용이 바뀌었을 때 갱신 (오래된 팁 표시용)
  status: 'draft' | 'published' | 'archived'
}
```

- `buildingId` 가 있으면 팁 상세에서 **"지도에서 보기"** 로 바로 이동한다. 지도 앱이라는 강점을 살리는 부분이다.
- `linkUrl` 은 팁의 근거를 남기기 위한 것이다. 학교 규정은 바뀌므로 출처 없는 팁은 게시하지 않는 것을 원칙으로 한다.
- `updatedAt` 이 1년 이상 지난 팁에는 "확인된 지 오래됐어요" 표시를 붙인다.

## 3. 단계별 도입

**1단계 — 앱 내 정적 데이터 (백엔드 배포 없이)**
- `src/data/tips.json` + `src/constants/tips.ts` (`appNotices.ts` 와 같은 방식)
- 팁 수정은 앱 재배포(또는 웹은 Netlify 재배포)가 필요하다. 웹판은 즉시 반영된다.
- 이유: 백엔드는 이번 배포와 별개로 스키마 변경·마이그레이션이 필요하다. 첫 출시를 막지 않도록 분리한다.

**2단계 — 백엔드 API + 관리**
- `tips` 테이블 (`db/create_tips_table.sql`, 기존 `db/` 마이그레이션 스크립트 방식). `ddl-auto=validate` 라 **SQL을 먼저 DB에 적용한 뒤** 엔티티를 배포해야 한다.
- 엔드포인트
  - `GET /tips?category=&cursor=` — 게스트 접근 허용(지도·공지와 동일 정책)
  - `GET /tips/{id}`
  - 쓰기(`POST/PUT/DELETE /admin/tips`)는 관리자 권한만. 앱 사용자용 쓰기 API는 만들지 않는다.
- 앱은 1단계 JSON을 **오프라인 폴백**으로 남긴다.

**3단계 (선택) — 알림·개인화**
- 기존 `notification_categories` 는 (user, category) 행 기반이라 `tips` 카테고리 값을 INSERT 하는 것만으로 구독을 붙일 수 있다.
- 신규 팁 푸시는 기본 꺼짐. 학기 초 시기성 팁만 제한적으로 발송한다(피로도 관리).
- 북마크는 기존 소식 북마크 구조를 재사용한다.

## 4. 화면 배치 (제안)

- **소식 탭 상단에 "생활 팁" 진입 카드** (가로 카테고리 칩 + 고정 팁 1~2개). 소식 목록과 섞이지 않게 한다.
- 팁 목록 → 상세(본문, 관련 건물 "지도에서 보기", 출처 링크, 북마크).
- 지도의 건물 시트(`BuildingSheet`)에는 해당 `buildingId` 팁이 있을 때만 "이 건물 팁 N개" 를 노출한다.
- 설정의 앱 공지(`NoticeListModal`)는 앱 자체 안내용으로 그대로 둔다. 팁을 거기 넣지 않는다.

## 5. 운영

- 작성 주체와 검수자를 1명씩 정한다(학생 팀원 작성 → 다른 팀원 검수). 근거 링크 없는 팁은 `draft` 로 둔다.
- 학기 시작 2주 전에 `season` 별 팁을 점검하는 체크리스트를 `docs/worklog.md` 에 남긴다.
- 개인정보·특정 교직원 실명·비공식 소문은 팁에 싣지 않는다.

## 6. 확인 필요 (결정해야 구현 가능)

1. **"하나의 단계"의 의미** — 소식 탭 안의 한 갈래(위 제안)인지, 하단 탭을 하나 더 두는 것인지, 온보딩 단계 중 하나인지. 이 문서는 소식 탭 안의 갈래로 가정했다.
2. **1단계(정적)로 먼저 갈지, 바로 백엔드까지 갈지.** 첫 출시가 임박했다면 1단계를 권한다.
3. **팁 작성자와 관리 방식** — 관리자 화면을 만들지, 당분간 SQL/JSON 직접 수정으로 갈지.
4. **카테고리 7종이 맞는지.** 앱의 알림 카테고리 7종(공지·장학·행사·수강·시설·취업·상담)과 맞출지 여부(BE README의 "가정 A" 와 같은 미확정 사항).
5. **초기 팁 원고** — 5~10개 정도의 실제 내용은 학교 공식 출처를 확인해서 채워야 한다. 임의로 만들지 않는다.
