# 제휴업체 데이터 충돌 기록

단과대별로 제휴업체 목록을 따로 받다 보니, **같은 가게가 여러 자료에 중복 등장**하면서
좌표·혜택·지점 범위가 서로 어긋나는 경우가 생긴다. 이 문서는 그 충돌을 모아
어떻게 판단했는지, 무엇이 아직 미해결인지 남긴다.

원본 데이터는 `src/constants/partners.ts` 한 곳에만 둔다. 이 문서는 그 파일에
담기 어려운 **판단 근거와 미해결 질문**을 기록하는 용도다.

마지막 갱신: 2026-09-08 (기숙사 자료 전량 반영, 신규 15곳 등록 — 현재 `partners.ts` 총 119개 지점. 이전 갱신(2026-08-20)의 "101개"는 그 사이 다른 세션에서 추가된 항목이 반영되지 않은 값이었다.)

---

## 1. 미해결 — 확인 필요

### 1.1 기숙사 제휴 신규 15곳 — 좌표·주소 전량 확보, 등록 완료

2026-09-08 세 차례에 걸쳐 받은 '기숙사' 제휴 목록 중 15곳이 신규였다. 첫 7곳(그린앤베리·
청년치킨 서교점·마포라스토랑·소금제면소 홍대·스니커즈 버거 클럽·AFC Kebab·Doner Kebab)은
같은 날 좌표·주소를 받아 먼저 반영했고, 나머지 8곳(시장을여는사람들 홍대점·별헤는잔·
피코·ZigZagg·코모이도이·레이브 에스프레소 바 상수·아리 스터디 카페·라곰필라테스)도
곧이어 좌표·주소를 받아 모두 등록했다. 더 이상 미결 항목 없음.

### 1.2 기숙사 혜택 이용 방법 — UI 반영 완료

2026-09-08에 받은 이용 방법("기숙사 카드키를 보여주기 / 기숙사 홈페이지 로그인 후
왼쪽 메뉴 선택창에서 거주 여부 보여주기")은 **개별 업체가 아니라 기숙사 소속 전체에
적용되는 공통 안내문**이라, 새 상수 `PARTNER_AFFILIATION_USAGE_NOTES`
(`src/constants/partnerAffiliations.ts`)를 만들어 소속 → 안내 문구로 매핑했다.

`PartnerSheet.tsx`에서 이 안내는 별도 구획이 아니라, 그 소속의 혜택 줄(기본
`benefit` 또는 `affiliationBenefits` 예외) **바로 아래에 구분선 없이** 붙는다 —
"기숙사 혜택"과 "그 이용 방법"이 하나의 구획으로 읽히도록 한 것.
브라우저(Safari/Chrome 모두)에서 `http://localhost:8081` → 캠퍼스 → 제휴 업체 검색으로
확인 가능.

### 1.3 기숙사 혜택 문구가 기존 자료와 다른 3곳 — `affiliationBenefits` 예외로 반영, 조건 재확인 필요

받은 문구를 그대로 `기숙사` 전용 예외로 넣었지만, 아래는 원래 소속과 조건이
달라 보여 표기 차이인지 실제 정책 차이인지 확인이 필요하다.

- **네코노유부 (`food-nekono-yubu`)** — 경영대학 자료는 포장 20% 할인에 "평일"
  제한이 있는데, 기숙사 자료는 이 제한을 언급하지 않는다.
- **제제집 (`food-jejejip`)** — 공과대학은 "1인 1메뉴 주문시 2인당 음료수 or 공깃밥 1개",
  기숙사는 "2인 음료수 1캔 / 3인 이상 된장찌개 1그릇"으로 조건·메뉴가 다르다.
- **아웃닭 홍대점 (`food-outdak-hongdae`)** — 공과대학은 "2인당 1마리 주문시" 조건이
  붙는데 기숙사 자료엔 이 조건이 없다.

### 1.4 소코아 홍대점 — 기숙사 자료도 "2~4인" 표기(§2.1과 동일한 옛 표기)

§2.1에서 이미 "2인 이상"으로 통일하기로 확정했는데, 기숙사 자료도 통일 전 옛 표기인
"2~4인"을 그대로 썼다. 이번엔 새로운 충돌로 보지 않고 기존 통일안(`2인 이상`)을
유지했다 — 예외 처리 안 함.

## 2. 해결됨 — 판단과 근거

### 2.1 소코아 홍대점 — 인원 조건 표기 차이

| 출처 | 혜택 |
|---|---|
| 공과대학·문과대학 | 1인 음료 1잔 / **2~4인** 사이드 택1 |
| 경영대학 | 1인 음료 1캔 / **2인 이상** 사이드 택1 |

- **판단:** 표기 오차. 사용자 확인을 거쳐 **"2인 이상"으로 통일**했다.
- **처리:** `benefit: '1인 음료 1잔 / 2인 이상 사이드 택1'`

### 2.2 서브웨이 상수점 — 적용 조건이 실제로 다름 ⚠️

| 출처 | 혜택 |
|---|---|
| 총학생회 | **학기 중** 단품/세트 10% 할인 |
| 경제학부 | 샌드위치·세트 전 품목 10% 할인(**사이드 메뉴만 구매 시 할인 미적용**) |

할인율은 같지만 제약이 서로 다르다. 총학생회는 기간 제한("학기 중"), 경제학부는
품목 제한("사이드 단독 구매 제외")이 붙는다. **한쪽으로 합칠 수 없다고 판단**했다.

- **처리:** 이 충돌 때문에 `Partner.affiliationBenefits` 필드를 도입했다(아래 §4 참고).
  기본 `benefit`은 총학생회 조건을 유지하고, 경제학부만 예외로 적었다.
- **현재 이 필드를 쓰는 유일한 항목이다.**

### 2.3 연어초밥 — 문구만 다름

| 출처 | 혜택 |
|---|---|
| 공과대학 | 인당 음료수 1개 서비스 |
| 경영대학 | 음료 1캔 제공 |

- **판단:** 같은 혜택의 다른 표현. 병합.
- **처리:** `affiliations: ['공과대학', '경영대학']`, 혜택은 기존 문구 유지.

### 2.4 또보겠지 떡볶이집 — 문구 차이 + **적용 지점 범위 차이**

혜택 내용은 양쪽 동일하다(2인 음료 / 3인 사리 / 4인 감자튀김).
다만 **제휴 지점 범위가 다르다.**

| 지점 | 공과대학 | 경영대학 |
|---|:---:|:---:|
| 깐따삐아점 | ○ | ○ |
| 해피토스점 | ○ | ○ |
| **스마일보이점** | ○ | **✕** |

- **판단:** 경영대학 자료에 스마일보이점이 없으므로 제외.
- **처리:** 깐따삐아·해피토스 두 지점에만 `'경영대학'`을 추가. 스마일보이점은
  `['공과대학']` 그대로.
- **주의:** 나중에 경영대학 자료가 보강되어 스마일보이점이 추가될 수 있다.
  누락인지 의도적 제외인지는 확인되지 않았다.

### 2.5 소코아 홍대점 — 좌표가 약 106m 어긋남

| 출처 | 좌표 (lat, lng) | 주소 |
|---|---|---|
| 공과대학·문과대학 자료 | `37.5493189, 126.9217977` | 서울 마포구 와우산로 15길 49 1층 |
| **경영대학 자료 (채택)** | **`37.548639, 126.920953`** | 서울 마포구 와우산로15길 49 1층 소코아 홍대점 |

주소는 사실상 동일한데 좌표가 다르다. 소수점 표기만 보면 비슷해 보이지만
실제 거리는 **약 106m**다(위도 차 `0.00068°` ≈ 76m, 경도 차 `0.00084°` ≈ 75m).
홍대 골목 기준으로 블록 하나 차이라 무시할 수 없는 값이다.

- **판단:** 사용자 결정으로 **경영대학 자료를 채택**했다.
- **처리:** `lat: 37.548639, lng: 126.920953`
- **되돌릴 때:** 현장 확인 결과 공대 자료가 맞으면 `37.5493189, 126.9217977`로 복구한다.
- **2026-08-20 재확인:** 공과대학·문과대학 최신 인스타그램 자료가 각각 독립적으로
  `37.5493189, 126.9217977`를 다시 보내왔다(두 소속 모두 동일 값). 다만 이는
  "현장 확인"이 아니라 같은 계열 자료의 재확인이라, **경영대학 좌표를 그대로 유지**
  하기로 사용자가 결정했다. 실제 현장 확인이 이뤄지면 그때 다시 판단한다.

### 2.6 연어초밥 / 경호네 — 같은 자리, 이름 표기 차이

| 출처 | 상호명 |

  실제로 쓰이는 이름은 '연어초밥' 쪽이라 **'경호네' 표기를 제거**했다(2026-09-08).

## 3. 데이터 입력 시 주의점

### 3.1 좌표 순서 — 제공 자료는 `경도, 위도` 순

받은 자료는 `126.920092, 37.548680` 형태, 즉 **경도(lng)가 먼저**다.
코드의 `Partner`는 `lat` / `lng` 필드를 쓰므로 **뒤집어서 넣어야 한다.**

```
자료: 126.920092, 37.548680
코드: lat: 37.548680, lng: 126.920092
```

홍대 일대 기준으로 위도는 `37.5x`, 경도는 `126.9x`라 눈으로 구분된다.

### 3.2 소속 명칭 — 자료의 통칭과 코드 유니온이 다를 수 있음

| 자료 표기 | 코드 유니온 (`PartnerAffiliation`) |
|---|---|
| "경제 대학" | `'경제학부'` |

`PartnerAffiliation`은 12종 고정 유니온이다. 자료에 없는 이름이 오면 임의로 추가하지 말고
어느 소속에 해당하는지 확인한다.

### 3.3 주소가 비어 있으면 대체로 중복 항목이다

단과대 자료에서 주소·좌표가 비어 있는 항목은, 그 단과대 담당자가 이미 다른 곳에
등록된 가게라고 판단해 생략한 경우가 많았다. 실제로 경영대학 자료의
연어초밥·또보겠지가 그랬다. **주소가 비어 있으면 먼저 이름으로 중복 검색한다.**

다만 **주소가 있어도 중복일 수 있다** — 소코아와 서브웨이가 그랬다.
새 자료를 넣기 전에는 항상 이름으로 전체 검색을 돌린다.

```bash
grep -n "가게이름" src/constants/partners.ts
```

### 3.4 좌표는 확인된 값만 넣는다

`partners.ts` 상단 주석의 원칙이다. 주소만 있고 좌표가 없으면 추정해서 넣지 말고
비워 두거나 확인을 요청한다.

## 4. `affiliationBenefits` — 소속별 예외 혜택

§2.2(서브웨이)처럼 **한 가게가 소속마다 다른 혜택을 주는 경우**를 표현하기 위해
`Partner`에 선택 필드를 추가했다.

```ts
// src/types/index.ts
export interface PartnerAffiliationBenefit {
  affiliation: PartnerAffiliation
  benefit: string
}

export interface Partner {
  // ...
  benefit?: string
  /** 소속별로 혜택이 다른 **예외만** 적는다. 여기 없는 소속은 benefit 을 따른다. */
  affiliationBenefits?: PartnerAffiliationBenefit[]
}
```

### 설계 의도

**"전면 전환"이 아니라 "예외만 기록"** 방식을 택했다. 대부분의 업체는 모든 제휴처에
같은 혜택을 주기 때문에, 76개 항목 전부를 배열 구조로 바꾸면 얻는 것 없이
데이터만 장황해진다. 실제로 이 필드를 쓰는 항목은 현재 **서브웨이 상수점 하나뿐**이다.

- `benefit` — 기본 혜택. 예외로 지정되지 않은 모든 소속에 적용된다.
- `affiliationBenefits` — 기본과 다른 소속만 나열한다.

### UI 표기

`src/components/map/PartnerSheet.tsx`의 혜택 카드 안에서, 기본 혜택 아래에
얇은 구분선을 두고 **소속 칩 + 해당 혜택**을 이어 붙인다. 별개 카드로 분리하지 않는 이유는
"다른 제휴"가 아니라 "이 소속만 조건이 다르다"로 읽혀야 하기 때문이다.

```
┌─ 제휴 혜택 ─────────────────────────
│ 학기 중 단품/세트 10% 할인
│ ─────────────────────────────────
│ [경제학부]
│ 샌드위치·세트 전 품목 10% 할인
│ (사이드 메뉴만 구매 시 할인 미적용)
└─────────────────────────────────
```

## 5. 백엔드 스키마에 미치는 영향

`partner_affiliations` 테이블은 현재 `(partner_id, affiliation)` 복합 PK 구조다.
§2.2 같은 케이스를 담으려면 **이 테이블에 `benefit` 컬럼이 필요하다.**

```sql
-- 현재
partner_id   bigint       NOT NULL  PRI
affiliation  varchar(50)  NOT NULL  PRI

-- 필요 (제안)
partner_id   bigint       NOT NULL  PRI
affiliation  varchar(50)  NOT NULL  PRI
benefit      varchar(500) NULL      -- NULL이면 partners.benefit 을 따른다
```

`GET /partners` 응답에서도 `affiliations`가 단순 문자열 배열이 아니라
`{ affiliation, benefit }` 형태여야 이 정보가 전달된다. 백엔드에 전달 필요.

관련 문서: `docs/schema-changes.md`
