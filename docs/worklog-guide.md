# 작업 로그 작성 가이드

`worklog.md`를 쓰는 이유와 형식. 기존 항목(2026-08-06~, 08-20, 08-24)에서 뽑아낸 규칙이므로, 새 항목도 이 형태를 따르면 서로 비교하며 읽기 쉽다.

## 언제 쓰나

- 커밋 메시지 하나로는 설명되지 않는 배경·결정 과정이 있을 때(왜 이 방향을 골랐는지, 무엇을 시도했다 버렸는지)
- 여러 파일에 걸친 작업을 마쳤을 때(세션 끝, 기능 하나 완료)
- 막힌 지점(미결)이 남아 다음에 이어받을 사람이 같은 조사를 반복하지 않게 해야 할 때

커밋 하나가 그 자체로 충분히 설명되면(간단한 버그 수정 등) 안 써도 된다. 커밋 히스토리 자체는 `커밋별-작업내역.docx`가 맡는다.

## 무엇을 쓰나 / 안 쓰나

- **쓴다**: 왜 이 방향으로 갔는지, 무엇을 확인했는지(수치·로그 포함), 무엇이 아직 안 끝났는지
- **안 쓴다**: `git diff`로 보이는 내용을 그대로 반복(커밋 메시지 몫), 코드 자체가 뭘 하는지 설명(주석 몫)

## 구조

1. **날짜 섹션**: `## YYYY-MM-DD` 또는 범위 `## YYYY-MM-DD ~ MM-DD`. 상대 날짜("어제", "이번 주") 대신 절대 날짜로 적는다.
2. **목표 줄**: `**목표**: ...`. 세션 중 방향이 바뀌었으면 `**목표 변화**: A → B → C`.
3. **변경된 파일 표** — `### 변경된 파일` 다음에:

   | 파일 | 변경 | 내용 |
   |---|---|---|
   | `path/to/file.ts` | `+N / -M` 또는 `신규`/`재작성` | 한 줄 요약 |

   표에 넣은 파일 중 아직 커밋 전인 게 섞여 있으면, 표 바로 아래 한 줄로 "커밋 `abc123`에 어디까지 담겼는지" 밝힌다(08-20 항목 참고).
4. **번호 매긴 하위 섹션** `### 1. <제목>`, `### 2. ...` — 항목마다 왜/무엇을/어떻게 확인했는지 서술체로 쓴다. 확인한 사실은 구체적 수치·로그를 남긴다(예: "HTTP 200, 333,436 B", "21/21 통과", "1 → 0 확인"). 표로 비교하면 명확한 경우(예: 같은 요청을 세 조건으로 보낸 결과) 표를 곁들인다.
5. 해결 안 된 부분은 `> **미결**: ...` 인용 블록으로 문단 끝에 눈에 띄게 남긴다.
6. 날짜 섹션 끝에는 `---` 구분선.

## 파일 맨 끝의 "살아있는" 섹션

날짜 섹션과 달리 매번 새로 만들지 않고 계속 갱신한다:

- **`## 다음 작업` 표** (`| 우선순위 | 항목 | 비고 |`) — 끝난 항목은 지우고, 새 항목은 우선순위에 맞는 자리에 끼워 넣는다.
- **`### 미결 질문`** — 답을 들으면 그 줄을 지운다. 새로 생기면 추가한다. 각 날짜 섹션에 적은 `> **미결**`이 여러 세션에 걸쳐 남아 있는 굵직한 질문이면 여기에도 옮겨 적어, 파일을 끝까지 안 읽어도 지금 뭐가 막혀 있는지 한눈에 보이게 한다.

## 문체

- 한국어. 개조식 나열보다 짧은 서술문을 우선한다.
- "무엇을 했다"보다 "왜 그렇게 했다"에 무게를 둔다 — 코드는 무엇을 했는지 이미 보여주므로.
- 실패했거나 보류한 시도도 남긴다(예: 제보 기능 백엔드 자체 구축을 시작했다가 중단한 사례) — 같은 길을 다시 시도하지 않게.
